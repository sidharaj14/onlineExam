# 08 — Evidence & Audit System: Media Capture, Non-Repudiation & Forensic Review

This document defines the architecture and protocols for evidentiary data capture, cryptographic integrity verification, storage hierarchy, access control, and administrative forensic review.

## 2. Screenshot Evidence Capture & Metadata Watermarking

### 2.1. Capture Trigger & Mechanism
When the Violation Engine flags a visual violation (`MULTIPLE_FACES`, `PROHIBITED_OBJECT`, `HEAD_POSE_ANOMALY`, `LOOKING_AWAY`, `FACE_ABSENT`):
1. The client captures the exact video frame from the active camera stream at full hardware resolution ($1280 \times 720$ or $1920 \times 1080$).
2. The frame is drawn onto an off-screen HTML5 `<canvas>`.
3. The system renders a bright red bounding box (thickness 3px) around the anomaly ROI (e.g. surrounding the detected smartphone or secondary face).
4. The system renders an indelible, tamper-evident metadata banner across the top:
   ```
   ========================================================================================================
   ACADEMIC INTEGRITY EVIDENCE | EXAM: EX-2026-CS101 | CANDIDATE: STU-8829 | UTC: 2026-09-11 05:22:15.302Z
   EVENT: PROHIBITED_OBJECT (cell phone) | CONFIDENCE: 0.89 | SEVERITY: HIGH (50 PTS) | FRAME HASH: SHA-256
   ========================================================================================================
   ```
5. The canvas is serialized to JPEG binary bytes (quality 0.85) and transmitted via `POST /api/v1/evidence/upload`.

### 2.2. Image Cryptographic Hashing
Upon receiving the binary payload, the backend immediately calculates its SHA-256 hash before disk persistence:
$$\text{Hash} = \text{SHA256}(\text{RawImageBytes})$$
This hash is written directly to the database `evidence_records.sha256_hash`. If a student claims an image was tampered with or fabricated, the file can be re-hashed against the immutable database entry.

## 3. Acoustic Evidence Clipping & Transcription

### 3.1. Ring-Buffer Audio Extraction
1. The client audio subsystem maintains a continuous rolling 4-second PCM ring buffer in browser memory.
2. When the Violation Engine confirms an acoustic violation (`SUSPICIOUS_SPEECH` or `BACKGROUND_CONVERSATION`):
   - The last 4 seconds of audio (2 seconds preceding the trigger + 2 seconds during the trigger) are extracted.
   - The buffer is encoded into a standard 16-bit Mono WAV format at 16,000 Hz.
3. The audio file is uploaded to the backend evidence repository.
4. The transcription snippet generated by Faster-Whisper, along with identified keywords, is attached as structured JSON metadata.

## 4. Evidence Storage Hierarchy & File Naming

Evidence assets are stored in a deterministic, partition-friendly directory structure on the server:

```
/storage/evidence/
  └── {exam_id}/
      └── {candidate_id}/
          ├── screenshots/
          │   ├── {evidence_id}_PROHIBITED_OBJECT_20260911_052215.jpg
          │   └── {evidence_id}_MULTIPLE_FACES_20260911_053102.jpg
          └── audio/
              └── {evidence_id}_SUSPICIOUS_SPEECH_20260911_052518.wav
```

- Filenames are prefixed with UUIDv4 (`evidence_id`) to prevent collision.
- Directories are segregated by `exam_id` and `candidate_id` to facilitate bulk archiving and automated retention purge routines.

## 5. Evidence Access Control & Security

1. **Authentication & Authorization**:
   - Evidence files are **never** hosted in an unauthenticated public `/static` directory.
   - Access to evidence media is gated through `GET /api/v1/evidence/{evidence_id}`.
   - Only authenticated Administrators with the `exam_reviewer` or `super_admin` role can access evidence media.
   - The candidate may only access their own evidence records if the institution explicitly enables post-exam review/dispute mode.
2. **Signed URLs / Ephemeral Access**:
   - For web playback, the backend generates short-lived, signed streaming tokens (valid for 15 minutes) bound to the admin's session IP.

## 6. Audit Logging System

Every security-sensitive state change in the system generates an append-only, immutable record in the `audit_logs` table:

```sql
CREATE TABLE audit_logs (
    id VARCHAR(36) PRIMARY KEY,
    timestamp TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    exam_id VARCHAR(36) NOT NULL,
    candidate_id VARCHAR(36),
    actor_id VARCHAR(36) NOT NULL,
    actor_role VARCHAR(20) NOT NULL,
    action VARCHAR(50) NOT NULL,
    ip_address VARCHAR(45) NOT NULL,
    details JSON NOT NULL,
    previous_hash VARCHAR(64),
    current_hash VARCHAR(64)
);
```

### Audited Actions
- `STUDENT_LOGIN_SUCCESS` / `STUDENT_LOGIN_FAILED`
- `BIOMETRIC_VERIFY_SUCCESS` / `BIOMETRIC_VERIFY_REJECTED`
- `EXAM_ATTEMPT_STARTED`
- `AI_ANOMALY_BUFFERED`
- `VIOLATION_CONFIRMED`
- `WARNING_ISSUED_W1` / `WARNING_ISSUED_W2`
- `WARNING_ACKNOWLEDGED_BY_STUDENT`
- `AUTOMATIC_DISQUALIFICATION_TRIGGERED`
- `ADMIN_DISMISSED_VIOLATION`
- `ADMIN_MANUAL_DISQUALIFY`
- `EXAM_SUBMITTED_SUCCESSFULLY`

## 7. Evidence Retention & Lifecycle Policies

| Tier | Lifecycle Stage | Retention Window | Storage Action |
| :--- | :--- | :--- | :--- |
| **Hot Storage** | Active Exam & Immediate Review | Exam Day + 7 Days | Fast local SSD storage; immediately streamable in Admin console. |
| **Warm Storage** | Disputed / Flagged Exams | 8 Days to 90 Days | Compressed ZIP archive with SHA-256 manifest; stored in institutional archive. |
| **Purge / Delete** | Compliant (Zero-Violation) Exams | 14 Days Post-Grading | Media files securely unlinked/shredded; metadata rows anonymized. |
